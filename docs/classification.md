# Classification and requests

Configured classifier workers apply deterministic personal rules, then validate overlapping semantic labels. The model cannot invent group participation or owner actions: the personal label requires recorded deterministic evidence or a source quote explicitly supporting an owner action/response. Group participation always uses the deterministic rule. Blocking, background, and update may overlap. Model output must contain at least one supported label, a reason, and a valid confidence or explicit null.

Every attempt records source revision, context generation, classifier/rules versions, personal evidence, state, and redacted failure code. A run is pending while inference is in progress. Transient failures retry with the durable queue's bounded backoff; only terminal failure assigns unorganized. Operator retry retains failure history and replaces unorganized after success. With no classifier configured, work remains queued rather than fabricating results.

Source edits/deletions, new conversation messages, changed personal overrides, and new derived photo text invalidate affected labels in the same transaction. The scheduler queues current generations and reevaluates group activity at exact seven-day message expiry with a daily fallback. A result computed while its source generation changes is recorded as superseded and cannot publish labels. Old classifications remain evidence history, never current labels.

Blocking messages can yield multiple tasks. Each request must quote an exact substring of source/derived text. Tasks retain immutable revision evidence and a stable extraction identity so retries do not duplicate requests. Consolidation requires a related conversation task ID and its exact existing title; Slack group/channel candidates must also belong to the same thread, unsupported IDs or invented quotes fail validation. Follow-ups preserve their own evidence.

Only a later source item with explicit extracted fulfillment evidence can resolve a task as done. Missing timing evidence or ambiguous fulfillment remains uncertain. Due dates do not complete tasks. Resolution evidence is stored with the source record/revision and quote. MCP does not expose task mutation; all status changes come from this ingestion/classification pipeline.

The local model adapter uses schema-constrained requests for classification and task extraction. Neither JSON schema nor exact quotation proves a model interpretation is correct; consumers receive evidence and uncertainty. See local-models.md for model pinning. Fixture inference and PostgreSQL checks verify overlap, newsletters, payment updates, retries, pending state, stale-generation rejection, multiple requests, follow-ups, uncertain fulfillment, and evidence-backed resolution. No live classifier inference is claimed until configured and exercised.
